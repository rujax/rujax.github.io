WARNING

起因

最近在做 Mod 时，需要批量将 DDS 格式的图片转变为 PNG 格式。
找了一圈，竟然没有找到合适好用的应用。
考虑了一下，不如自己撸一个简单的吧。

选型

因为应用的功能比较单一，所以不打算使用 Qt 来实现。
正好也看看其他桌面应用框架发展到什么程度了。

基于 Go 的桌面应用框架

搜索相关关键字，基本推荐的都是 Fyne ，随即开始试用。

在逐个功能试用到文件对话框 dialog.FileDialog 时，意外发现它竟然不支持多选。

而我这个应用恰恰是需要多选的，在 issues 搜索到了已经有人问了相关的问题。
令我有些不解的是，这个 issue 从2020年6月6日就被人提出，直到现在快6年了，依然没有实现。

更有意思的是，最近的 开发者回复 是在今年（2026年）3月17日，内容如下：

有点难评，就不评了。撤！！！

基于 Rust 的桌面应用框架

搜索相关关键字，推荐的前几个有： Tauri 、 Slint 、 Iced 。

下面说说没有选择这 3 个框架的原因：

  • Tauri：不喜欢前端使用 HTML/CSS/JS，后端使用 Rust 的方式
  • Slint：不太喜欢声明式构建应用的方式
  • Iced：使用指南做得极烂，而且目前依然处于 实验性质 的阶段

就当我准备放弃基于 Rust 的桌面应用框架时，无意间发现了 native-windows-gui 。

native-windows-gui

根据介绍文档，可以得知该库是对 Windows API 的简单封装。

Win32 API 早已有所耳闻，是出了名的晦涩难懂。有一种外星人留言的美感 <(￣ˇ￣)/
虽然 Rust 也在语法怪异上不相上下，但总还是比直接看 Win32 API 好一些（笑

感想

摸索了几天，在反反复复走了不少弯路后，总算完成了。说说感想吧。

不便之处

  1. 功能非常基础，几乎没有自定义的可能
  2. 布局只能支持到一层子布局，稍微复杂一点的布局暂时没找到解决方案
  3. 文档和示例并不是很完善
  4. 指南推荐的使用 native-windows-derive 的宏写法实际上坑不少（最后放弃重写，意外顺畅很多
  5. 自定义使用数据成员变量非常麻烦
  6. 事件系统耦合比较严重

最大优点

编译后的可执行程序文件大小非常小：
内嵌了应用图标之后，也只有 2.12 MB（如果不内嵌图标的话，是 1.33 MB）。

与之对比的是，使用 Qt 新建一个程序，不新写任何一行代码，
直接以 Release 模式编译并发布后的所有文件大小接近 30 MB (´⊙ω⊙`)

Note

Qt6Core.dll + Qt6Gui.dll + Qt6Widgets.dll 这 3 个必不可少的库文件加起来就有 28.3 MB 了 ╮(╯_╰)╭

结语

最后，放上我花了几天摸爬滚打写出来的拙作吧： DDS2Any （图标也是我自己瞎画的 < (￣︶￣)>

Note

2026-06-05 更新：基于 Tauri 和其他技术重写的版本： DDS2Any v0.1.4

Important

DDS2Any v0.2.3

  • 支持拖拽添加图片文件
  • 输入格式增加“任意”，支持的格式可以一次性转换
  • 支持语言增加 English
